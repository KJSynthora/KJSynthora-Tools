Databricks Administration & Governance

This is the layer above writing PySpark: who can see what data, how it's organized across an entire organization, and how you migrate off the older way of doing it. It's asked more at mid-to-senior level, but even junior interviews increasingly touch Unity Catalog since it's now the default for any new Databricks workspace.

Why no "Run" buttons here: these are account/workspace admin console and governance concepts — there's no metastore, no real users/groups, and nothing to meaningfully execute in a browser sandbox. This page focuses on getting the architecture and exact commands right.
Metastores

Hive Metastore (Legacy)

The Hive Metastore (HMS) is the original, older way Databricks tracked table metadata (schemas, locations, partitions) — a per-workspace catalog with only a two-level namespace (schema.table, no catalog level). Access control was coarse: either table ACLs enabled on a cluster, or relying on cloud storage permissions (IAM passthrough) directly — nothing centrally governed across workspaces. If your organization has multiple Databricks workspaces, each historically had its own completely separate Hive Metastore with no shared governance between them.

Interview angle: The core limitation to name: Hive Metastore has no concept of a "catalog" and no cross-workspace governance — every workspace is an island.

Unity Catalog

Unity Catalog (UC) is Databricks' modern governance layer: a metastore created once per region and attached to every workspace in that region, giving one shared, centrally governed view of all data across the organization. It adds a three-level namespace (catalog.schema.table), fine-grained GRANT/REVOKE permissions on tables, views, volumes and functions, built-in data lineage tracking, and centralized audit logging — none of which Hive Metastore had.

ScopePer-workspacePer-region, shared across workspaces
Namespaceschema.tablecatalog.schema.table

The Unity Catalog Object Model

The hierarchy, top to bottom: Metastore (one per region) → Catalog (a top-level grouping, e.g. one per environment or business unit) → Schema (a.k.a. database — groups related tables) → Table / View / Volume / Function. Volumes are a UC-specific concept for governing access to non-tabular files (raw files, ML model artifacts) the same way tables govern structured data.

Metastore (per region)
  └── Catalog: prod
        └── Schema: sales
              ├── Table: orders
              ├── View: monthly_summary
              └── Volume: raw_invoices  ← file storage, governed like a table
Migration

Hive Metastore → Unity Catalog: The Approaches

There isn't one forced method — the right approach depends on how much you need to preserve. Manual recreation (CREATE TABLE pointing at the same storage path) works for a handful of tables. For anything larger, Databricks provides an "Upgrade to Unity Catalog" wizard directly in Catalog Explorer that upgrades an HMS table/schema in place. For an entire estate, Databricks Labs' open-source UCX toolkit assesses what needs migrating (permissions, table formats, cluster configs) and automates much of the process.

ApproachBest For
Manual CREATE TABLE / SYNCA handful of tables, full control over naming
"Upgrade to Unity Catalog" UI wizardAd-hoc, table-by-table or schema-by-schema migration
UCX (Databricks Labs toolkit)Whole-workspace migration, permission mapping, assessment reporting

The SYNC Command

SYNC is the SQL command underlying most upgrade workflows — it creates (or updates) a Unity Catalog table/schema that mirrors an existing Hive Metastore one, without copying the underlying data files when the table is external (it just registers the same storage location under UC's governance). This makes it a metadata-only operation for external tables, which is fast and low-risk compared to physically moving data.

-- Migrate a single table
SYNC TABLE main.sales.orders FROM hive_metastore.sales.orders;

-- Migrate an entire schema at once
SYNC SCHEMA main.sales FROM hive_metastore.sales;

-- Preview what SYNC would do without actually doing it
SYNC TABLE main.sales.orders FROM hive_metastore.sales.orders DRY RUN;
Interview angle: Know the key distinction — SYNC re-registers external tables' existing storage location under UC (fast, no data movement); managed tables generally require an actual data copy (e.g. CREATE TABLE AS SELECT) since UC manages their storage location itself.

Migration Gotchas

A few things that trip up real migrations: existing cluster configs and init scripts that assume Hive Metastore access patterns often need updating for UC's access model; permissions don't automatically carry over — HMS table ACLs and UC grants are separate systems, so access needs to be re-granted deliberately (this is exactly what UCX's assessment step is for); and managed vs. external table distinctions matter more under UC, since UC managed tables store data in a UC-controlled location rather than wherever the original HMS table happened to live.

Admin Roles

Account, Metastore & Workspace Admins

Three distinct admin scopes, easy to conflate in an interview answer. An Account Admin operates at the very top — manages the whole Databricks account, billing, and can create/assign metastores across all workspaces. A Metastore Admin governs one Unity Catalog metastore specifically — can create catalogs, grant/revoke at the catalog level, and manage metastore-wide settings. A Workspace Admin is scoped to a single workspace — manages workspace users, cluster policies, and workspace-level settings, but doesn't inherently control Unity Catalog data governance unless separately granted metastore privileges.

Interview angle: "Can a Workspace Admin grant access to a Unity Catalog table?" — Not automatically. Workspace Admin and data governance (Unity Catalog privileges) are deliberately separate concerns; a Workspace Admin needs an explicit UC grant (or Metastore Admin rights) to manage table-level access.

Ownership & Privilege Inheritance

Every UC object (catalog, schema, table) has an owner — by default, whoever created it — who can grant/revoke privileges on it regardless of broader admin roles. Privileges also inherit downward: granting USE CATALOG + USE SCHEMA + SELECT at the catalog level cascades to every schema and table beneath it, so you rarely need to grant permissions table-by-table for broad access patterns.

Identity: Users, Groups, SPNs

Users & Groups

A user is an individual human identity — in most enterprise setups, synced in from Microsoft Entra ID rather than created manually inside Databricks. A group is a named collection of users (and service principals) that permissions get granted to collectively — the standard practice is "grant to the group, not the individual," so access changes when someone joins/leaves a group instead of requiring a manual permission edit per person.

Service Principals

A Service Principal (SPN) is a non-human identity for automated processes — an ADF pipeline calling a Databricks job, or a CI/CD deployment script. It's registered in Microsoft Entra ID first, then added to the Databricks account and granted permissions exactly like a user would be. This is what lets an ADF pipeline authenticate to run a Databricks notebook without any human's credentials being involved.

Interview angle: This connects directly back to the Azure identity guide — prefer a Managed Identity over a Service Principal with a stored secret whenever the calling service supports it, for the same "nothing to leak or rotate" reason.

SCIM Provisioning

SCIM (System for Cross-domain Identity Management) is the standard protocol Databricks uses to automatically sync users and groups from an identity provider like Microsoft Entra ID into the Databricks account console — so when someone joins a team's Entra ID group, they automatically appear (and get the corresponding access) in Databricks too, without anyone manually adding them in two places.

Governance Queries

GRANT / REVOKE / SHOW GRANTS

The actual SQL commands you'll use to manage Unity Catalog access day to day. Grants target an object (catalog, schema, table, or even a specific column via row/column-level security) and a principal (a user, group, or service principal).

GRANT USE CATALOG ON CATALOG main TO `data-analysts`;
GRANT SELECT ON TABLE main.sales.orders TO `data-analysts`;
REVOKE SELECT ON TABLE main.sales.orders FROM `contractor-group`;

-- See what's currently granted
SHOW GRANTS ON TABLE main.sales.orders;
SHOW GRANTS TO `data-analysts`;

System Tables (Audit & Lineage)

Unity Catalog exposes its own operational data as queryable tables under the system catalog — genuinely just SQL you can run. system.access.audit logs who did what and when (every query, every grant change). system.information_schema.* exposes metadata about every catalog, schema, table, and column you have access to — the standard way to answer "which tables reference this column" or "who can see this table" programmatically instead of clicking through the UI.

-- Recent access to a sensitive table
SELECT * FROM system.access.audit
WHERE request_params.table_full_name = 'main.sales.orders'
ORDER BY event_time DESC;

-- Every table in a catalog, with owner
SELECT table_catalog, table_schema, table_name, table_owner
FROM system.information_schema.tables
WHERE table_catalog = 'main';
Interview angle: "How would you audit who accessed a sensitive table last month?" — system.access.audit, filtered by table name and event_time. Knowing this table exists (rather than assuming you'd need external logging) is the actual signal interviewers are checking for.

Is There a DataFrame Way to Do This?

Mostly no, deliberately. Unity Catalog governance (GRANT/REVOKE, catalog/schema management, user/group administration) is a control-plane concern, not a data-processing one — so it's managed via SQL (as above), the Databricks UI, the REST API, or Terraform (for infrastructure-as-code setups), not through PySpark DataFrame transformations. The one place PySpark does interact with this layer is simply reading data governed by it — once a user's permissions are granted, spark.table("main.sales.orders") or a %sql SELECT ... cell in a notebook just works or fails based on those same UC grants, with no separate DataFrame-level permission API to learn.

Interview angle: If asked "how do you grant DataFrame access to a table," the correct redirect is that DataFrame code doesn't have its own permission model — access is enforced at the table level by Unity Catalog regardless of whether you touch it via SQL or the DataFrame API.
