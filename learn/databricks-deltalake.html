Databricks & Delta Lake, the way interviews actually ask about it

This is your actual job stack, and the single most-tested area beyond raw SQL/PySpark syntax. Each item below is something that comes up constantly — either as a direct question ("what does OPTIMIZE do?") or baked into a scenario question ("how would you handle duplicate records arriving daily?").

Why this page has no "Run" buttons: Delta Lake's real behavior — the transaction log, time travel, file compaction — only exists on an actual Spark cluster with a Delta-enabled storage layer. A browser sandbox can't fake that honestly, so this page focuses on getting the concepts and exact syntax right instead.
Databricks Basics

What Is Databricks

Databricks is a managed platform that runs Apache Spark for you, adding notebooks, job scheduling, cluster management, and (via Delta Lake) reliable table storage on top of cloud storage like ADLS or S3. Think of it as: Spark is the processing engine, Delta Lake is the storage format that makes that engine's tables behave reliably, and Databricks is the platform that hosts and orchestrates both.

Interview angle: Be ready to explain the relationship between these three in one sentence — interviewers often use this to check you're not just pattern-matching syntax without understanding the stack.

Clusters & Cluster Types

A cluster is the actual compute (one driver node + worker nodes) that runs your Spark jobs. All-Purpose clusters are for interactive notebook work (shared, kept running, more expensive per hour). Job clusters spin up just for a scheduled job and terminate when it finishes (cheaper, isolated). Autoscaling lets a cluster add/remove worker nodes based on load instead of running a fixed size the whole time.

# Not code you write daily — but know the distinction:
All-Purpose Cluster  → notebooks, ad-hoc exploration, shared by a team
Job Cluster           → one scheduled pipeline run, then terminates
Autoscaling           → min/max worker count, scales with workload
Interview angle: "Why would you use a Job cluster instead of an All-Purpose cluster for a nightly pipeline?" — cost (it doesn't idle) and isolation (one job's failure doesn't affect others sharing a cluster).

DBFS & Mounting Storage

DBFS (Databricks File System) is a filesystem abstraction layered over cloud storage, so your code can use simple paths instead of full cloud URLs. In practice, most modern setups use Unity Catalog external locations or mount ADLS/S3 buckets so notebooks can read/write via a clean path.

# Reading a file via a mounted path
df = spark.read.format("csv").option("header", True).load("/mnt/raw/orders.csv")

# Reading directly from ADLS (modern approach, no mount needed with proper auth)
df = spark.read.format("parquet").load("abfss://container@account.dfs.core.windows.net/path/")

Widgets & Parameters

Widgets let a notebook accept parameters at runtime — essential when ADF or a Job triggers the same notebook with different inputs (like a date or environment name) instead of hardcoding values.

dbutils.widgets.text("run_date", "2024-01-01")
run_date = dbutils.widgets.get("run_date")

# ADF's "Notebook" activity passes parameters that land here as widgets
Delta Lake Fundamentals

Why Delta Lake (vs Plain Parquet)

Plain Parquet files on cloud storage have no concept of transactions — if a write fails halfway, you can be left with a corrupted, half-updated table, and there's no way to see "what did this table look like yesterday." Delta Lake adds a transaction log on top of Parquet files, giving you ACID guarantees, time travel, and safe concurrent reads/writes — while the underlying data files are still just Parquet.

Interview angle: The one-line answer interviewers want: "Delta Lake = Parquet files + a transaction log that adds ACID transactions, time travel, and schema enforcement."

The Transaction Log

Every write to a Delta table creates a new JSON entry in the _delta_log folder describing exactly which files were added or removed. Readers reconstruct the table's current state by replaying this log, which is what makes ACID transactions and time travel possible — the log is the actual source of truth, not just "whatever files happen to be in the folder."

# Folder structure of a Delta table on storage:
/orders/
  part-0001.parquet
  part-0002.parquet
  _delta_log/
    00000000000000000000.json   # version 0
    00000000000000000001.json   # version 1
    ...

Creating a Delta Table

Delta is the default table format in Databricks, so creating a managed table is often just a normal CREATE TABLE — but you'll also frequently write a DataFrame out directly in Delta format, especially in a Bronze ingestion layer.

-- SQL
CREATE TABLE orders (order_id INT, customer_id INT, amount DOUBLE)
USING DELTA;

-- PySpark
df.write.format("delta").mode("overwrite").saveAsTable("orders")
Delta Lake Operations

MERGE INTO (Upserts)

This is the single most-asked Delta Lake operation in interviews. MERGE INTO lets you insert new records and update existing ones in one atomic statement — the standard way to handle "load today's changes into a table that already has yesterday's data" (a classic upsert / SCD Type 1 pattern).

MERGE INTO target_table t
USING source_updates s
ON t.id = s.id
WHEN MATCHED THEN UPDATE SET t.amount = s.amount, t.updated_at = s.updated_at
WHEN NOT MATCHED THEN INSERT (id, amount, updated_at) VALUES (s.id, s.amount, s.updated_at);
Interview angle: Be ready to explain why this is safer than "DELETE then INSERT" — MERGE is one atomic operation (via the transaction log), so a failure partway through can't leave the table half-updated.

Time Travel

Because every change is recorded as a numbered version in the transaction log, you can query a Delta table as it existed at an earlier version or timestamp — useful for debugging ("what did this look like before yesterday's bad load?"), auditing, or recovering from an accidental bad write.

SELECT * FROM orders VERSION AS OF 12;
SELECT * FROM orders TIMESTAMP AS OF '2024-01-15';

-- PySpark
df = spark.read.format("delta").option("versionAsOf", 12).table("orders")

-- Roll a table back to an earlier version
RESTORE TABLE orders TO VERSION AS OF 12;

Schema Enforcement & Evolution

By default, Delta enforces schema — a write with a mismatched or extra column fails loudly instead of silently corrupting the table (unlike plain Parquet, which just writes whatever it's given). When a schema change is intentional, you opt in to schema evolution explicitly rather than have it happen by accident.

# Enforcement is the default — this fails if new_column isn't in the table already:
df.write.format("delta").mode("append").saveAsTable("orders")

# Explicitly allow the new column to be added:
df.write.format("delta").mode("append").option("mergeSchema", "true").saveAsTable("orders")
Performance & Maintenance

Partitioning & the Small File Problem

Partitioning splits a table's files into subfolders by a column (commonly a date), so queries filtering on that column can skip reading irrelevant data entirely. But partitioning too finely (e.g., by hour on a low-volume table) creates the small file problem — thousands of tiny files that slow reads down instead of speeding them up, since opening each file has overhead regardless of its size.

df.write.format("delta").partitionBy("order_date").saveAsTable("orders")

# Rule of thumb: partition by a column with reasonable cardinality
# (hundreds, not millions, of distinct values) and enough data per partition.

OPTIMIZE & Z-ORDER

OPTIMIZE compacts many small files into fewer, larger ones — the direct fix for the small file problem after it's already happened. ZORDER BY goes further, physically co-locating related values (e.g., rows with similar customer_id) within those compacted files, so filters on that column can skip even more data.

OPTIMIZE orders;
OPTIMIZE orders ZORDER BY (customer_id);
Interview angle: Know the distinction — OPTIMIZE alone fixes file count/size; ZORDER additionally improves data skipping for specific filter columns. They're often used together.

VACUUM

Old, no-longer-referenced data files (left behind after updates, deletes, or OPTIMIZE compactions) aren't deleted immediately — they're kept around to support time travel. VACUUM permanently removes files older than a retention threshold (default 7 days) to reclaim storage. Running it with too short a retention window can break time travel or in-flight reads, so it's usually a scheduled maintenance job, not an ad-hoc command.

VACUUM orders RETAIN 168 HOURS;  -- 7 days, the safe default
Architecture

Medallion Architecture (Bronze / Silver / Gold)

The standard Databricks pattern for organizing a lakehouse into layers of increasing refinement. Bronze holds raw, unmodified ingested data (schema-on-read, keep everything, including bad records). Silver holds cleaned, validated, deduplicated data with a consistent schema. Gold holds business-level aggregates ready for reporting or Power BI. Each layer is typically its own set of Delta tables.

Bronze:  raw JSON/CSV landed as-is, minimal transformation
   ↓
Silver:  cleaned, deduplicated, joined, typed correctly
   ↓
Gold:    aggregated, business-ready (e.g., daily_revenue_by_region)
Interview angle: Extremely commonly asked as "walk me through how you'd design a pipeline for X" — structuring your answer around Bronze/Silver/Gold signals you know the standard pattern rather than improvising.

Structured Streaming Basics

Structured Streaming lets you write the same DataFrame code for streaming data as for batch data — Spark handles the incremental processing. A checkpoint location tracks progress so a restarted stream picks up where it left off instead of reprocessing or losing data. This is commonly used for near-real-time Bronze ingestion from sources like Event Hubs or Kafka.

stream_df = spark.readStream.format("delta").table("bronze_events")

query = (stream_df.writeStream
    .format("delta")
    .option("checkpointLocation", "/checkpoints/silver_events")
    .outputMode("append")
    .trigger(processingTime="1 minute")
    .table("silver_events"))
Governance & Orchestration

Unity Catalog

Unity Catalog is Databricks' governance layer: a three-level namespace (catalog.schema.table, instead of just schema.table) that centralizes permissions, auditing, and data lineage across every workspace in an organization, rather than managing access separately per workspace.

SELECT * FROM main.sales.orders;
--          ^catalog ^schema ^table

GRANT SELECT ON TABLE main.sales.orders TO `analyst-team`;

Workflows & Jobs

Databricks Workflows (formerly "Jobs") schedule and orchestrate notebooks, SQL queries, or Python scripts — either standalone or as a chain of dependent tasks (a DAG). In many shops, ADF triggers the overall pipeline and calls a Databricks Job/notebook as one activity within it, rather than the two tools competing for the same job.

Interview angle: "Would you orchestrate with ADF or Databricks Workflows?" — a reasonable answer is that ADF often owns the broader pipeline (moving data between systems, triggers, monitoring across the estate), while Databricks Workflows own the internal task dependencies within the Spark processing itself.
