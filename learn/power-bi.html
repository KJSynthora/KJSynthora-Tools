Power BI, from the data engineer's side of the fence

You're not becoming a full-time BI developer — but you're the one feeding Power BI its data, and you'll be expected to understand enough of the modeling and DAX side to have an intelligent conversation about why a report is slow, or how a Gold table should be shaped.

Why no "Run" buttons here: Power BI is a desktop application and cloud service — there's no way to execute DAX or a data model inside a browser sandbox. This page focuses on getting the concepts and DAX syntax exactly right.
Power BI Basics

Desktop, Service, and Power Query

Power BI Desktop is where you build reports and data models on your machine. Power BI Service (app.powerbi.com) is the cloud platform where published reports are hosted, refreshed, and shared. Power Query is the ETL layer inside Desktop — where you connect to sources, filter/reshape data, and clean it up before it ever reaches the data model, using a point-and-click interface that generates M code behind the scenes.

Import vs. DirectQuery vs. Live Connection

This is the single most consequential decision in a Power BI design, and a very common interview question. Import copies the data into Power BI's own compressed in-memory engine (fastest reports, but data is only as fresh as the last refresh). DirectQuery leaves data in the source and sends live queries on every interaction (always fresh, but only as fast as the source system, and DAX capability is more limited). Live Connection is similar to DirectQuery but specifically for connecting to an existing Power BI dataset or Analysis Services model rather than a raw data source.

ModeData FreshnessPerformanceBest For
ImportAs of last refreshFastest (in-memory)Most reports; datasets that fit in memory
DirectQueryReal-timeDepends on sourceHuge datasets, near-real-time requirements
Live ConnectionReal-timeDepends on source modelReusing an existing published dataset
Interview angle: "Your source table has 500 million rows and business wants near-real-time numbers — which mode?" — DirectQuery, accepting the performance tradeoff, possibly combined with Aggregations (see below) to speed up common queries.

Power Query (M) Basics

Every transformation you apply in Power Query's Editor (filter rows, rename a column, change a type, merge two queries) becomes a recorded, ordered Applied Step written in the M language behind the scenes. This step-by-step recipe re-runs every time the data refreshes — it's genuinely a lightweight ETL tool, not just a preview pane.

// Simplified M code for "filter, then add a column" — visible in the Advanced Editor
let
    Source = Sql.Database("server", "database"),
    Filtered = Table.SelectRows(Source, each [order_date] >= #date(2024,1,1)),
    Added = Table.AddColumn(Filtered, "Year", each Date.Year([order_date]))
in
    Added
Data Modeling

Star Schema in Power BI

The same star schema concept from data warehousing applies directly here: one central fact table (orders, sales — the numbers you measure) surrounded by dimension tables (customer, product, date — the things you slice by), connected by relationships. Power BI's DAX engine is specifically optimized for this shape; flattening everything into one giant table, or modeling a snowflake with many small linked dimension tables, both tend to hurt both performance and usability.

Interview angle: If asked to model a Gold-layer table for Power BI, describe it in star schema terms explicitly — it signals you understand the consumption layer, not just the pipeline that produced it.

Relationships & Cardinality

A relationship connects two tables on a common column. Cardinality describes the shape of that relationship — one-to-many is by far the most common (one customer, many orders). Cross-filter direction controls which table's filters flow to the other: single direction (dimension filters fact — the standard, safest choice) or both (bidirectional — powerful but can cause ambiguous filter paths and performance issues if overused).

Interview angle: "When would you use bidirectional filtering?" — Sparingly: many-to-many bridge tables, or specific scenarios needing a dimension to be filtered by the fact table. Default to single-direction unless you have a specific reason not to.

Data Model Best Practices

A few habits that come up repeatedly: hide surrogate/foreign key columns from report view (users shouldn't see raw IDs), mark a proper Date table as the official date table (unlocks time intelligence functions), and prefer star schema over one flat wide table even though a flat table feels simpler — the flat approach breaks down fast once you need multiple fact tables or complex time intelligence.

DAX Fundamentals

Calculated Columns vs. Measures

A calculated column is computed once per row, at refresh time, and stored in the model (uses memory, like a real column). A measure is computed on the fly, at query time, in whatever context the visual is currently showing (a total, a specific slice, a specific row of a table) — it's never stored. As a rule of thumb: use a measure for aggregations (sums, ratios, counts) and a calculated column only when you genuinely need a static per-row value to filter or group by.

// Calculated column — evaluated once per row, stored
Full Name = Employees[FirstName] & " " & Employees[LastName]

// Measure — evaluated dynamically based on current filter context
Total Sales = SUM(Sales[Amount])

Row Context vs. Filter Context

This is the single hardest DAX concept, and the one that separates people who've memorized DAX syntax from people who actually understand it. Row context exists when a formula is being evaluated one row at a time (a calculated column, or inside iterator functions like SUMX). Filter context is the set of filters currently applied to the whole calculation — from slicers, visual axes, or explicit CALCULATE arguments — and it's what makes the same measure return different numbers in different cells of a table or chart.

// This measure has no row context — it's evaluated once per visual cell,
// under whatever filter context that cell represents (e.g. "Region = West, Year = 2024")
Total Sales = SUM(Sales[Amount])

// SUMX introduces row context explicitly, row by row, then sums the results
Total With Tax = SUMX(Sales, Sales[Amount] * (1 + Sales[TaxRate]))
Interview angle: If asked to explain context, use exactly this framing: filter context = "which rows are visible right now," row context = "which single row am I looking at right now" — and note that CALCULATE is the main tool for manipulating filter context deliberately.

CALCULATE — the Core DAX Function

CALCULATE evaluates an expression in a modified filter context — it's how you build "total sales, but only for last year" or "total sales, ignoring the region filter" on top of a base measure. Nearly every non-trivial DAX pattern (time intelligence, percent-of-total, exceptions to a filter) is CALCULATE wrapping a simpler measure with new filter arguments.

Sales Last Year =
CALCULATE(
    [Total Sales],
    SAMEPERIODLASTYEAR('Date'[Date])
)

// Total sales ignoring whatever region is currently sliced
Sales All Regions =
CALCULATE(
    [Total Sales],
    ALL(Region)
)

Common DAX Functions

A working vocabulary covers most interview questions and real report-building: SUM/AVERAGE/COUNTROWS for basic aggregation, SUMX/AVERAGEX (the "X" iterator functions, which loop row by row before aggregating — needed when the calculation itself varies per row), DISTINCTCOUNT for unique counts, FILTER to build a filtered table for use inside CALCULATE, and ALL / ALLEXCEPT to remove filters from part or most of the model.

Total Orders = COUNTROWS(Orders)
Unique Customers = DISTINCTCOUNT(Orders[CustomerID])
High Value Orders = CALCULATE(COUNTROWS(Orders), FILTER(Orders, Orders[Amount] > 1000))

Time Intelligence

A family of built-in DAX functions for date-based comparisons that would otherwise require manual date math: TOTALYTD/TOTALQTD/TOTALMTD for running totals within a period, SAMEPERIODLASTYEAR and DATEADD for period-over-period comparisons. All of these require a proper Date table marked as such in the model to work correctly.

Sales YTD = TOTALYTD([Total Sales], 'Date'[Date])

Sales Growth vs LY =
DIVIDE(
    [Total Sales] - CALCULATE([Total Sales], SAMEPERIODLASTYEAR('Date'[Date])),
    CALCULATE([Total Sales], SAMEPERIODLASTYEAR('Date'[Date]))
)
Interview angle: DIVIDE (not the / operator) is the expected way to handle division in DAX — it safely returns BLANK instead of erroring on divide-by-zero, similar to SQL's NULLIF pattern.
Performance

Incremental Refresh

Instead of reloading an entire fact table on every refresh, incremental refresh partitions it by date and only reloads recent partitions (say, the last 7 days), while older partitions stay untouched. This is essential once a table grows large — a full daily reload of years of history becomes both slow and unnecessary.

Query Folding

When Power Query's transformation steps can be translated back into a single query against the source system (a SQL WHERE clause, for instance) instead of pulling all the raw data down and filtering it locally, that's query folding — and it's dramatically faster. Some transformations (certain custom M functions, merging data from different source types) break folding, silently forcing Power BI to pull everything down first. Checking whether folding is happening (via "View Native Query" in the Applied Steps) is a real, practical skill.

Aggregations & Composite Models

An aggregation table stores pre-summarized data (e.g., daily totals instead of every transaction) at Import speed, while the underlying detailed table stays in DirectQuery — Power BI automatically routes a query to the fast aggregated table when possible, and falls back to the detailed DirectQuery table only when a report needs finer granularity. A composite model is this pattern generalized: mixing Import and DirectQuery tables in the same model.

Your Stack

Connecting Power BI to Databricks

Power BI connects to Databricks via the built-in Databricks connector, pointing at a SQL Warehouse (Databricks' SQL-optimized compute endpoint) rather than an all-purpose cluster — SQL Warehouses are specifically tuned for this kind of concurrent, ad-hoc BI query pattern. You can choose Import (snapshot the Gold table into Power BI) or DirectQuery (query Databricks live on every interaction) exactly as with any other source.

In Power BI Desktop: Get Data → Databricks
  Server hostname:   your-workspace.azuredatabricks.net
  HTTP path:         /sql/1.0/warehouses/xxxxxxxxxxxx
  Catalog:           main   (Unity Catalog)
  Table:             sales.gold.daily_revenue
Interview angle: "Would you point Power BI at the Gold layer or the Silver layer?" — Gold, always: it's already business-aggregated and modeled for consumption, so Power BI isn't re-deriving business logic that belongs in the pipeline.

Row-Level Security (RLS)

RLS restricts which rows a user can see in a report based on their identity — a regional manager should only see their own region's data, from the same published report everyone else uses. It's implemented as a DAX filter expression tied to a role, then that role is mapped to users or Entra ID groups in the Power BI Service.

// RLS role "RegionManager" — filter expression on the Region table
[RegionName] = USERPRINCIPALNAME()

// or, mapping via a separate security table joining users to allowed regions
