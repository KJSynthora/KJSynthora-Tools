Azure, the parts a Data Engineer actually gets tested on

You don't need to be a cloud architect. You need to know how these services fit together well enough to explain your own pipeline end to end, and answer the handful of security/networking questions that come up in almost every Data Engineer interview.

Why no "Run" buttons here: these are Azure portal and infrastructure concepts — pipelines, networking, identity — not something a browser sandbox can execute. This page focuses on getting the concepts, terminology, and relationships exactly right.
Azure Data Factory

Your daily orchestration tool — given the most depth here.

Pipelines, Activities, Datasets

A pipeline is a logical grouping of activities — the individual steps (copy data, run a notebook, execute a stored procedure, run a lookup). A dataset represents a specific piece of data within a data store (a table, a file, a folder) that an activity reads from or writes to. Think: pipeline = the recipe, activities = the steps, datasets = the ingredients.

Pipeline: "DailyOrdersLoad"
  → Activity: Copy Data      (source dataset: SQL table  →  sink dataset: ADLS csv)
  → Activity: Databricks Notebook   (transform Bronze → Silver)
  → Activity: Stored Procedure       (update a watermark/control table)

Linked Services

A linked service is the connection string / credentials definition for an external system (a SQL Server, an ADLS account, a Databricks workspace) — datasets then reference a linked service rather than embedding credentials themselves. This separation means you can point the same pipeline at dev vs. prod just by swapping which linked service it uses.

Interview angle: "How would you avoid hardcoding a database password in a pipeline?" — reference a Key Vault-backed linked service instead of typing the secret directly into ADF.

Triggers

Triggers decide when a pipeline runs. Schedule triggers run on a fixed recurrence (daily at 2am). Tumbling Window triggers run on fixed, non-overlapping time intervals and are aware of dependencies between windows (useful for backfills — each window "knows" its own time range). Event-based triggers fire when a file lands in storage (Blob created/deleted). Manual triggers just mean someone (or another system) calls it on demand.

Trigger TypeFires WhenTypical Use
ScheduleFixed recurrenceNightly batch load
Tumbling WindowFixed, sequential time slicesBackfills, time-aware reprocessing
Event-basedA file appears/disappears in storageReact to file drops from an upstream system
ManualOn demandAd-hoc runs, testing
Interview angle: Tumbling Window vs Schedule is a common trip-up — Tumbling Window is specifically designed for scenarios needing backfill/replay of specific historical windows; Schedule just fires and moves on.

Integration Runtime (IR)

The IR is the actual compute that executes activities. Azure IR is fully managed by Microsoft, used for cloud-to-cloud movement. Self-Hosted IR is software you install on a VM inside your own network — required when ADF needs to reach an on-premises database or a resource behind a private network that Azure IR can't see. Azure-SSIS IR exists specifically to lift-and-shift legacy SQL Server Integration Services packages into ADF.

Interview angle: "Your source database is on-prem behind a firewall — how does ADF reach it?" — Self-Hosted IR, installed on a VM that has network access to that on-prem system.

Parameterization & Dynamic Content

Hardcoding a table name or a date into a pipeline means you need a near-duplicate pipeline for every variation. Parameters let a pipeline accept values at runtime; dynamic content (ADF's expression language, wrapped in @{}) lets you build strings, dates, and conditions from those parameters — the same pipeline can then load any table or any date range just by being called differently.

// A dataset's file path built from pipeline parameters:
@concat('raw/', pipeline().parameters.source_table, '/', formatDateTime(utcnow(), 'yyyy-MM-dd'), '.csv')

Mapping Data Flows vs. a Databricks Notebook Activity

Mapping Data Flows are ADF's built-in, no-code visual transformation tool (joins, aggregations, derived columns) — it compiles down to Spark under the hood but you never write code. A Databricks Notebook activity instead calls out to a real Databricks notebook you've written in PySpark/SQL. Most Spark-fluent teams (like yours) prefer the notebook activity for anything non-trivial, since it's more powerful, testable, and reusable outside ADF; Data Flows are more common in low-code-preference teams or for simple transformations.

Monitoring, Retry & Failure Handling

ADF's Monitor tab shows pipeline run history, activity-level status, and error details. Individual activities support a configurable retry count and interval for transient failures (a brief network blip shouldn't fail the whole pipeline). For anything more deliberate, you can wire an alert (via Azure Monitor) or a failure-path activity (ADF supports "on failure" dependency conditions between activities, so you can trigger a notification or cleanup step specifically when something breaks).

Interview angle: "A pipeline failed at 3am — walk me through how you'd debug it." Mention: check Monitor for which activity failed and its error message, check whether it's a transient issue retry would have fixed, check upstream data (did the source file even land), and where alerting fits in so you'd know before being asked.
Storage

ADLS Gen2 — where your Bronze/Silver/Gold tables actually live.

ADLS Gen2 Basics

Azure Data Lake Storage Gen2 is Blob Storage with a hierarchical namespace enabled — meaning it behaves like a real filesystem with directories, rather than blob storage's flat "container + key" model. This matters for big data workloads because operations like renaming or deleting a "folder" become a single fast metadata operation instead of touching every individual file.

storage_account/
  container (a.k.a. "filesystem")/
    bronze/orders/2024/01/15/file.parquet
    silver/orders/file.parquet
    gold/daily_revenue/file.parquet

Access Tiers & Lifecycle Management

Blob storage tiers trade cost for retrieval speed: Hot (frequent access, highest storage cost, cheapest to read), Cool (infrequent access, cheaper storage, small retrieval cost), Archive (rarely accessed, cheapest storage, hours of latency to retrieve). Lifecycle management policies automatically move data between tiers (or delete it) based on age — e.g., move Bronze data to Cool after 30 days.

RBAC vs ACLs on Storage

ADLS Gen2 supports two overlapping permission systems. RBAC (Azure roles like Storage Blob Data Contributor) controls access at the container/account level. POSIX-style ACLs allow finer-grained control down to individual folders/files, similar to Linux file permissions. In practice, most teams set broad RBAC roles and layer folder-level ACLs only where genuinely needed (e.g., restricting one team's Silver folder from another team).

Compute

Not your daily tool as a data engineer, but comes up around Self-Hosted IR and cost questions.

Virtual Machines — Just Enough

A VM is a full virtual computer you provision and manage yourself (OS, patching, scaling). As a data engineer, you rarely provision VMs directly for data processing — Databricks manages that compute for you — but you'll encounter VMs specifically as the host for a Self-Hosted Integration Runtime, or occasionally for a jump box to reach a private network.

Interview angle: Don't over-invest here — know that VMs exist, what they're for in your stack (Self-Hosted IR), and that Databricks abstracts cluster VM management away from you day-to-day.
Networking

Increasingly asked about, since most real pipelines run inside a locked-down network.

VNets & Subnets

A Virtual Network (VNet) is an isolated private network inside Azure. Subnets divide it into smaller segments — you might put your Databricks clusters in one subnet and a Self-Hosted IR VM in another, each with different access rules. Resources inside the same VNet can talk to each other privately; resources need explicit configuration to reach anything outside it.

Private Endpoints

By default, a service like ADLS or Key Vault has a public internet endpoint (protected by keys/RBAC, but still internet-reachable). A Private Endpoint gives that service a private IP address inside your VNet instead, so traffic never leaves Microsoft's private network — a common security requirement in enterprise environments, and increasingly a default expectation in interviews about "how would you secure this pipeline."

Interview angle: "How do you prevent your storage account from being reachable from the public internet?" — Private Endpoint + disabling public network access on the storage account.

Network Security Groups (NSGs)

An NSG is a basic firewall — a list of allow/deny rules (by port, protocol, source/destination) applied to a subnet or network interface. It's the layer that decides, for example, whether a VM's subnet can even attempt to reach the outside internet at all, independent of what identity/RBAC permissions a user might have.

Security & Identity

Nearly every interview touches this — how do your pipelines authenticate safely?

Key Vault

Key Vault stores secrets (connection strings, passwords, API keys), certificates, and encryption keys centrally, so they never need to be hardcoded into a pipeline, notebook, or config file. ADF Linked Services and Databricks secret scopes can both reference a Key Vault directly — your code references a secret name, and the actual value is resolved securely at runtime.

# Databricks notebook reading a Key Vault-backed secret scope:
password = dbutils.secrets.get(scope="kv-scope", key="sql-db-password")

Microsoft Entra ID (formerly Azure AD)

Entra ID is Azure's identity provider — it's what authenticates users, and also hosts non-human identities like Service Principals and Managed Identities that let applications and services authenticate to each other. Every RBAC role assignment ("who can access what") is granted to an identity that Entra ID manages.

Managed Identity vs. Service Principal

Both let a service (like ADF or Databricks) authenticate to another service (like ADLS) without a human's credentials. A Service Principal is an application identity you register yourself, with a secret or certificate you must manage and rotate. A Managed Identity is automatically created and managed by Azure for a specific resource (like an ADF instance) — there's no secret to store or rotate at all, since Azure handles the credential lifecycle internally. Managed Identity is the preferred, more secure default whenever it's available.

Interview angle: "Why prefer Managed Identity over a Service Principal with a stored secret?" — no secret to leak, rotate, or expire; Azure manages the credential lifecycle entirely.

RBAC (Role-Based Access Control)

RBAC assigns roles (collections of permissions, like Reader, Contributor, or resource-specific ones like Storage Blob Data Contributor) to an identity (a user, group, service principal, or managed identity) at a scope (Management Group → Subscription → Resource Group → individual Resource — permissions inherit downward). The guiding principle is least privilege: grant the narrowest role at the narrowest scope that still lets the job get done.

Scope hierarchy (permissions inherit downward):
Management Group
  └── Subscription
        └── Resource Group
              └── Resource (e.g., one storage account)

Example: grant a Databricks managed identity read access to just one storage account,
not Contributor access to the whole subscription.
Interview angle: Be ready to name least privilege explicitly if asked "how would you grant Databricks access to this storage account?" — the expected shape of the answer is a specific role (like Storage Blob Data Contributor) at the narrowest useful scope, assigned to a Managed Identity, not a broad role at the subscription level.
