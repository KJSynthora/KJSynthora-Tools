Lesson 3.1
INNER JOIN — The Foundation
Returns only rows where a match exists in BOTH tables

A JOIN lets you query data from two or more tables at once, combining rows based on a related column. Before JOINs, you'd need to write multiple queries and manually match results — tedious and error-prone.

The INNER JOIN is the most common JOIN. It returns rows where the join condition is true in both tables. If a row in Table A has no matching row in Table B, it's excluded from results. Think of it as the intersection of two sets.

💡 Key insight: SQL databases are designed around relational data — tables that reference each other via foreign keys. JOINs are how you "re-join" that data at query time.

INNER JOIN syntax:
SQL 
SELECT
    e.id,
    e.name,
    e.salary,
    d.dept_name
FROM employees e
INNER JOIN departments d
    ON e.dept_id = d.id  -- join condition
ORDER BY e.name;

Lesson 3.2
LEFT JOIN, RIGHT JOIN, FULL OUTER JOIN
Including non-matching rows with NULL values

Outer JOINs preserve rows that don't have a match in the other table. Non-matching columns become NULL. This is critical for finding "orphaned" records, data gaps, and ensuring completeness in reports.

LEFT JOIN

Returns all rows from the left table, plus matching rows from the right. Non-matching right-side columns are NULL.

SQL
SELECT
    e.name,
    e.salary,
    d.dept_name
FROM employees e
LEFT JOIN departments d
    ON e.dept_id = d.id;
Result — all 5 employees, NULLs where no dept matches:
namesalarydept_name
Alice85,000Engineering
Bob72,000Marketing

🎯 Power technique: Finding employees WITHOUT a department
SQL
SELECT e.name, e.salary
FROM employees e
LEFT JOIN departments d
    ON e.dept_id = d.id
WHERE d.id IS NULL  -- only unmatched!
✅ Pattern to memorize: LEFT JOIN + WHERE right_table.id IS NULL = "rows in A with no match in B". This is used constantly in data cleaning and auditing.
RIGHT JOIN

Mirror of LEFT JOIN. Returns all rows from the right table, plus matching rows from the left. In practice, RIGHT JOIN is rarely used because you can always rewrite it as a LEFT JOIN by swapping table order.

SQL
-- This RIGHT JOIN...
SELECT e.name, d.dept_name
FROM employees e
RIGHT JOIN departments d ON e.dept_id = d.id;

-- ...is identical to this LEFT JOIN:
SELECT e.name, d.dept_name
FROM departments d
LEFT JOIN employees e ON e.dept_id = d.id;

FULL OUTER JOIN

Returns all rows from both tables. Rows without a match on either side get NULL values for the missing columns. Not supported in MySQL — use UNION of LEFT and RIGHT JOINs instead.

SQL
-- Works in PostgreSQL, SQL Server, Oracle
SELECT e.name, d.dept_name
FROM employees e
FULL OUTER JOIN departments d
    ON e.dept_id = d.id;

-- MySQL workaround:
SELECT e.name, d.dept_name FROM employees e LEFT JOIN departments d ON e.dept_id = d.id
UNION
SELECT e.name, d.dept_name FROM employees e RIGHT JOIN departments d ON e.dept_id = d.id;
Lesson 3.3
SELF JOIN & Joining 3+ Tables
Joining a table to itself, and chaining multiple JOINs

A SELF JOIN joins a table to itself. It sounds strange, but it's essential for hierarchical data — like an employee table where each employee has a manager_id that references another employee in the same table.

👥 employees (with manager hierarchy)
idnamemanager_id
1Sarah (CEO)NULL
2Alice1
3Bob1
4Carol2
5Dave2
SQL — SELF JOIN
-- List each employee alongside their manager's name
SELECT
    e.name       AS employee,
    m.name       AS manager
FROM employees e           -- alias "e" = employee
LEFT JOIN employees m      -- alias "m" = manager (same table!)
    ON e.manager_id = m.id
ORDER BY m.name NULLS FIRST;

🔑 Aliases are required: When joining a table to itself, you MUST use aliases to distinguish the two "copies" of the table. The database treats them as two separate tables with different names.
Joining 3+ Tables

You can chain as many JOINs as needed. Each JOIN adds a new table. The key is understanding the data model — which tables share which keys.

SQL — 3 Table JOIN
-- employees → departments → locations
SELECT
    e.name,
    d.dept_name,
    l.city,
    l.country
FROM employees e
INNER JOIN departments d  ON e.dept_id    = d.id
INNER JOIN locations   l  ON d.location_id = l.id
WHERE l.country = 'India'
ORDER BY e.name;
✅ Best practice: Always use table aliases (e, d, l) when joining multiple tables. Without them, ambiguous column names cause errors — and the query becomes unreadable.
🎯
ON vs WHERE for Filtering
Put join conditions in ON. Put filtering conditions in WHERE. Mixing them works for INNER JOINs but breaks OUTER JOINs in subtle ways.
⚡
Join Order Performance
Most query optimizers handle join order automatically. But joining smaller filtered tables first can improve performance on very large datasets.
🔑
Always Use Aliases
Use short, memorable aliases: e for employees, d for departments, o for orders. This becomes essential when joining 3+ tables.
⚠️
Cartesian Product Danger
Forgetting the ON clause creates a CROSS JOIN — every row paired with every other row. 1000 × 1000 rows = 1,000,000 rows returned.
Lesson 3.4
UNION vs UNION ALL vs JOIN
Combining rows vs combining columns — fundamentally different operations

JOINs combine columns — they take rows from multiple tables and combine them side-by-side based on a key. UNION combines rows — it stacks the results of two queries on top of each other (like appending rows).

JOIN — Combines Columns
Merges related tables horizontally. Result has MORE columns. Requires a matching key between tables.
employees JOIN departments ON e.dept_id = d.id
UNION — Combines Rows
Stacks query results vertically. Result has SAME columns. Both queries must have the same number of columns and compatible types.
SELECT name FROM current_employees UNION SELECT name FROM former_employees
UNION vs UNION ALL:
SQL
-- UNION: removes duplicates (slower — runs DISTINCT)
SELECT name, email FROM customers_2023
UNION
SELECT name, email FROM customers_2024;

-- UNION ALL: keeps duplicates (faster — no dedup step)
SELECT name, email FROM customers_2023
UNION ALL
SELECT name, email FROM customers_2024;

-- UNION to simulate FULL OUTER JOIN in MySQL:
SELECT e.name, d.dept_name FROM employees e LEFT JOIN departments d ON e.dept_id=d.id
UNION
SELECT e.name, d.dept_name FROM employees e RIGHT JOIN departments d ON e.dept_id=d.id;

⚡ Rule of thumb: Use UNION ALL by default unless you explicitly need to remove duplicates. UNION ALL is always faster because it skips the deduplication step.

💪 Challenge 1
Easy
Task: Write a query that returns the names and salaries of all employees, along with their department name. Employees without a department should still appear — with NULL for department name.
Use LEFT JOIN. LEFT JOIN preserves all rows from the left (employees) table even when there's no matching row in the right (departments) table.
Solution
SELECT
    e.name,
    e.salary,
    d.dept_name
FROM employees e
LEFT JOIN departments d
    ON e.dept_id = d.id
ORDER BY e.name;
💪 Challenge 2
Medium
Task: Find all departments that have NO employees assigned to them. Return only the department name.
Start with departments as the LEFT table. Join employees on dept_id. Then filter WHERE employee.id IS NULL — this catches departments with no matching employee rows.
Solution
SELECT d.dept_name
FROM departments d
LEFT JOIN employees e
    ON e.dept_id = d.id
WHERE e.id IS NULL  -- departments with NO employees
💪 Challenge 3
Hard
Task: Using SELF JOIN on the employees table (which has a manager_id column referencing the same table), write a query that shows each employee's name, their manager's name, and the manager's salary. Only include employees who HAVE a manager (skip the CEO who has no manager).
Alias the employees table twice: e for employees and m for managers. JOIN employees e ON e.manager_id = m.id. Use INNER JOIN (not LEFT) to exclude the CEO who has no manager.
Solution
SELECT
    e.name        AS employee,
    m.name        AS manager,
    m.salary      AS manager_salary
FROM employees e
INNER JOIN employees m
    ON e.manager_id = m.id
-- INNER JOIN: excludes CEO (no manager_id)
ORDER BY m.name;

Question 1 of 5
Which JOIN returns rows only when a match exists in BOTH tables?
A LEFT JOIN
B INNER JOIN
C FULL OUTER JOIN
D CROSS JOIN
✅ Correct! INNER JOIN returns only rows where the join condition is TRUE in both tables. Rows without a match are excluded from results.
Question 2 of 5
What will this query return for the non-matching rows?
SELECT e.name, d.dept_name
FROM employees e
LEFT JOIN departments d ON e.dept_id = d.id
A Those rows are excluded from results
B An error is thrown
C dept_name will be NULL for those rows
D dept_name will be an empty string
✅ Correct! LEFT JOIN keeps all rows from the left table (employees). Where no department match exists, the dept_name column becomes NULL — not empty string, not excluded.
Question 3 of 5
You want to find all customers who have NEVER placed an order. Which pattern is correct?
A INNER JOIN orders WHERE orders.id IS NULL
B LEFT JOIN orders WHERE orders.id IS NULL
C RIGHT JOIN orders WHERE orders.id IS NULL
D FULL JOIN WHERE both sides are NULL
✅ Correct! LEFT JOIN customers → orders, then WHERE orders.id IS NULL. This "anti-join" pattern is one of the most useful SQL patterns — it finds rows in A with no match in B.
Question 4 of 5
What's the key difference between UNION and UNION ALL?
A UNION ALL is only for JOINs, UNION is for stacking rows
B UNION allows different column counts, UNION ALL requires matching columns
C UNION removes duplicates; UNION ALL keeps all rows including duplicates
D They are identical — UNION ALL is just older syntax
✅ Correct! UNION runs a DISTINCT operation to remove duplicate rows — slower. UNION ALL keeps every row including duplicates — faster. Use UNION ALL by default unless deduplication is required.
Question 5 of 5
A SELF JOIN requires:
A A special SELF keyword in SQL
B The same table referenced twice with different aliases
C Two separate tables with identical schema
D A recursive CTE — there's no SELF JOIN syntax
✅ Correct! SELF JOIN is just a regular JOIN where you reference the same table twice with different aliases (e.g., FROM employees e INNER JOIN employees m ON e.manager_id = m.id). There's no special keyword.
Module Summary
What you've learned in Module 3
  • ✓ INNER JOIN returns only rows with matches in both tables — non-matching rows are excluded
  • ✓ LEFT JOIN preserves all left-table rows; non-matching right-table columns become NULL
  • ✓ RIGHT JOIN is the mirror of LEFT JOIN — almost always rewritable as a LEFT JOIN
  • ✓ FULL OUTER JOIN returns all rows from both tables with NULLs where no match exists
  • ✓ Anti-join pattern: LEFT JOIN + WHERE right.id IS NULL finds rows in A with no match in B
  • ✓ SELF JOIN joins a table to itself using two different aliases — used for hierarchical data
  • ✓ 3+ table joins chain multiple JOINs — always use table aliases
  • ✓ JOIN combines columns; UNION combines rows — fundamentally different operations
  • ✓ UNION ALL is faster than UNION — use it unless you need deduplication
  • ✓ Forgetting the ON clause creates a CROSS JOIN — potentially millions of unwanted rows
