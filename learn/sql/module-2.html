Combining Conditions — AND / OR / NOT / BETWEEN / IN

In Module 1 you filtered with a single WHERE condition. Real queries almost always need multiple conditions. SQL gives you logical operators to combine them: AND, OR, NOT, and range shortcuts BETWEEN and IN.

AND — both conditions must be true

AND returns rows where every condition is true. Think of it as narrowing your filter.

SQL
SELECT * FROM orders WHERE city = 'Mumbai' AND status = 'delivered';

OR — at least one condition must be true

OR returns rows where any one condition is true. It broadens your filter.

NOT inverts a condition — returns everything that does not match.

BETWEEN — range filter (inclusive)

BETWEEN x AND y matches values from x to y, including both endpoints. It works on numbers, dates, and text.

💡 BETWEEN = >= AND <=
WHERE amount BETWEEN 20000 AND 50000 is exactly the same as WHERE amount >= 20000 AND amount <= 50000. BETWEEN is just cleaner.
SQL
-- Orders with amount between ₹20,000 and ₹50,000 SELECT customer, product, amount FROM orders WHERE amount BETWEEN 20000 AND 50000;
✅ Result — 3 rows

GraceTablet42000

IN — match against a list of values

IN (val1, val2, ...) matches if the column equals any value in the list. It replaces multiple OR conditions cleanly.

SQL
-- Orders from Mumbai or Delhi (using IN) SELECT customer, city, amount FROM orders WHERE city IN ('Mumbai', 'Delhi'); -- NOT IN — exclude a list SELECT customer, status FROM orders WHERE status NOT IN ('cancelled', 'pending');

Combining Multiple Operators — Use Parentheses!

⚠️ Operator Precedence Trap
SQL evaluates AND before OR. Always use parentheses to make your intent explicit, otherwise your query logic can be completely wrong.
SQL — Precedence Example
-- BUG: AND is evaluated first, so this is wrong WHERE city = 'Mumbai' OR city = 'Delhi' AND amount > 50000 -- Read as: Mumbai OR (Delhi AND amount > 50000) -- All Mumbai rows returned — even small amounts! -- CORRECT: use parentheses to be explicit WHERE (city = 'Mumbai' OR city = 'Delhi') AND amount > 50000;

Pattern Matching — LIKE & Wildcards

Exact matches with = are great, but what if you need to find all products whose name starts with "Phone" or all emails from Gmail? That's where LIKE and wildcard characters come in.

%
Percent — Any Characters
Matches zero or more characters in any position.
'Lap%' → Laptop, Laptop Pro, Lap
'%phone%' → Phone, Earphone, Smartphone
_
Underscore — One Character
Matches exactly one character at that position.
'T_blet' → Tablet
'Ph__e' → Phone

LIKE examples

SQL
-- Products starting with 'L' SELECT customer, product FROM orders WHERE product LIKE 'L%'; -- Products containing 'let' anywhere SELECT customer, product FROM orders WHERE product LIKE '%let%'; -- NOT LIKE — exclude pattern SELECT customer, product FROM orders WHERE product NOT LIKE '%phone%';
✅ LIKE 'L%' — Products starting with L
customerproduct
AliceLaptop
EveLaptop
🔠 Case Sensitivity
In MySQL and SQLite, LIKE is case-insensitive for ASCII characters. In PostgreSQL, LIKE is case-sensitive — use ILIKE for case-insensitive matching. In SQL Server, it depends on the collation.

Underscore _ wildcard

SQL
-- Exactly 5-character products: Ph + 3 chars SELECT product FROM orders WHERE product LIKE 'Ph___'; -- Matches 'Phone' -- 6-character cities SELECT DISTINCT city FROM orders WHERE city LIKE '______'; -- 6 underscores → Mumbai, Delhi (both 6 chars)

DISTINCT — remove duplicate values

DISTINCT eliminates duplicate rows from the result. Useful when you need a unique list of values from a column.

SQL
-- All unique cities in the orders table SELECT DISTINCT city FROM orders; -- All unique products SELECT DISTINCT product FROM orders ORDER BY product; -- DISTINCT on multiple columns SELECT DISTINCT city, status FROM orders;
✅ DISTINCT cities — 3 unique cities
city
Mumbai
Delhi
Chennai
⚡ Performance Note
DISTINCT requires extra sorting/deduplication work. For large tables, use it only when truly needed. Often a GROUP BY with aggregation (next lesson) is a better approach.

Aggregate Functions — COUNT, SUM, AVG, MIN, MAX

Aggregate functions collapse multiple rows into a single value. Instead of seeing 1000 order rows, you can instantly know: total revenue, average order value, highest and lowest amounts — with one query.

COUNT()
Count rows
Number of rows matching the condition. COUNT(*) counts all rows, COUNT(col) ignores NULLs.
COUNT(*) → 7 (all orders)
SUM()
Total sum
Adds up all values in a numeric column. NULLs are ignored.
SUM(amount) → 290500
AVG()
Average
Mean value of a numeric column. SUM ÷ COUNT (non-NULL rows).
AVG(amount) → 41500
MIN()
Minimum
Smallest value. Works on numbers, dates, and text (alphabetically).
MIN(amount) → 3500
MAX()
Maximum
Largest value. Same rules as MIN.
MAX(amount) → 95000
COUNT DISTINCT
Unique count
Counts unique non-NULL values in a column.
COUNT(DISTINCT city) → 3
SQL — All Aggregates in One Query
SELECT COUNT(*) AS total_orders, SUM(amount) AS total_revenue, ROUND(AVG(amount), 0) AS avg_order_value, MIN(amount) AS min_order, MAX(amount) AS max_order, COUNT(DISTINCT city) AS unique_cities FROM orders;
✅ Result — dashboard in a single row
total_orderstotal_revenueavg_order_valuemin_ordermax_orderunique_cities
7290500415003500950003

Aggregates with WHERE filter

Combine WHERE with aggregates to compute summaries on a filtered subset.

SQL
-- Revenue from delivered orders only SELECT COUNT(*) AS delivered_count, SUM(amount) AS delivered_revenue, AVG(amount) AS avg_delivered FROM orders WHERE status = 'delivered';
✅ Delivered orders only
delivered_countdelivered_revenueavg_delivered
319500065000
🚫 Common Mistake — Mixing Aggregates and Regular Columns
SELECT customer, SUM(amount) FROM orders — This will fail or return unpredictable results in most databases! When you use an aggregate, every non-aggregate column must be in a GROUP BY clause (next lesson covers this).

Lesson 2.4 · 18 min

GROUP BY and HAVING — Grouping Data

Aggregates in Lesson 2.3 summarized the entire table into one row. GROUP BY lets you get a separate aggregate for each group — total revenue per city, orders per status, etc. HAVING then filters those groups.

📋 SQL Clause Execution Order (Critical!)
SQL clauses execute in this order, regardless of how you write them:

1. FROM → select the table
2. WHERE → filter individual rows
3. GROUP BY → group the remaining rows
4. HAVING → filter the groups
5. SELECT → compute the output columns
6. ORDER BY → sort results
7. LIMIT → limit rows returned

This is why you cannot use HAVING to filter before grouping, and why WHERE cannot reference aggregate functions.

GROUP BY — aggregate per group

SQL
-- Total orders and revenue per city SELECT city, COUNT(*) AS total_orders, SUM(amount) AS total_revenue, ROUND(AVG(amount),0) AS avg_order FROM orders GROUP BY city ORDER BY total_revenue DESC;
✅ Revenue by city — 3 groups

HAVING — filter the groups

HAVING is like WHERE, but it filters after grouping — so you can filter based on aggregate values. You cannot use aggregate functions in WHERE.

🚫 WHERE vs HAVING — The Most Common Confusion
WHERE filters individual rows before grouping.
HAVING filters groups after grouping.

❌ WHERE SUM(amount) > 50000 → ERROR — cannot use aggregate in WHERE
✅ HAVING SUM(amount) > 50000 → CORRECT
SQL
-- Cities with total revenue > ₹100,000 SELECT city, COUNT(*) AS orders, SUM(amount) AS total_revenue FROM orders GROUP BY city HAVING SUM(amount) > 100000 ORDER BY total_revenue DESC;
✅ Only cities with >₹100K revenue — 1 group
cityorderstotal_revenue
Delhi3159000

WHERE + GROUP BY + HAVING — the full picture

SQL
-- Delivered orders only (WHERE filters first) -- Then group by city and find cities with 1+ delivered orders SELECT city, COUNT(*) AS delivered_orders, SUM(amount) AS delivered_revenue FROM orders WHERE status = 'delivered' -- ← filter BEFORE grouping GROUP BY city HAVING COUNT(*) >= 1 -- ← filter AFTER grouping ORDER BY delivered_revenue DESC;
✅ Delivered revenue per city
